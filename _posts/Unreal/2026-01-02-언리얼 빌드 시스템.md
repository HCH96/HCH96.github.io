## 언리얼 에디터(Unreal Editor)

언리얼 에디터(Unreal Editor)는 에픽 게임즈가 제공하는 **게임 제작용 저작 도구**이다.

- 언리얼 에디터는 **게임을 플레이하는 프로그램이 아니다**
- **게임을 만들기 위한 도구**이며, 개발 환경이다

즉, 언리얼 엔진으로 작업할 때는 항상 에디터 단계 (개발자 관점)와 게임 빌드 단계 (유저 관점)를 명확히 구분해서 생각해야 한다.

--- 

## 언리얼 엔진의 구성

언리얼 엔진을 기준으로 보면 결과물은 크게 두 가지로 나뉜다.

### 에디터(Editor)

- 게임 제작을 위해 제공되는 응용 프로그램
- 기획, 로직 작성, 에셋 배치, 테스트를 수행
- 개발자는 이 에디터 안에서 모든 작업을 완료한다

### 게임 빌드(Game Build)

- 실제 유저가 실행하는 **독립 실행 게임**
- EXE 파일 + 리소스(콘텐츠)로 구성
- 에디터와 달리 **개발용 기능은 제거**된 상태

에디터에서 모든 개발을 마친 뒤 **게임 빌드 과정을 통해 최종 게임을 만든다**.

---

## 언리얼 에디터의 특징

언리얼 에디터는 자유도가 높은 대신, **강하게 정해진 규칙 기반 구조**를 가지고 있다.  
프로젝트를 구성하는 **폴더 구조, 파일 이름 규칙, 모듈 구성 방식**이 모두 미리 정의되어 있으며, 이 규칙에 따라 에디터와 빌드 시스템이 동작한다.

즉, 언리얼 엔진에서는 내가 임의로 폴더를 만들고 코드를 배치하는 방식이 아니라, **엔진이 요구하는 구조에 맞춰 프로젝트를 설계하고 확장해 나가는 방식**이 기본 전제이다.

이 규칙을 제대로 이해하지 못하면, 프로젝트 전반에서 다음과 같은 문제가 발생하기 쉽다.

- 에디터의 소스 인식 실패  
- 빌드 실패  
- 의도하지 않은 의존성 문제

따라서 언리얼 개발에서는 자유롭게 구성한다기보다는 **정해진 규칙을 정확히 이해하고 그 안에서 확장한다**는 관점이 중요하다.


## 언리얼 에디터 실행 방식

### uproject 파일

언리얼 프로젝트는 `.uproject` 확장자를 가진 파일을 기준으로 관리된다.

- 이 파일을 더블 클릭하면 에디터가 실행된다
- 단순한 바로가기 파일이 아니라, 프로젝트에 사용될 엔진 버전과 모듈 정보 등이 저장된 파일이다

### 실행 흐름

uproject 실행 과정은 다음과 같다.

1. `.uproject` 확장자는 윈도우 레지스트리에 등록되어 있음
2. 더블 클릭 시 **UnrealVersionSelector** 프로그램이 실행됨
3. UnrealVersionSelector는
   - 어떤 엔진 버전이 필요한지 확인
   - 해당 버전의 에디터 실행 파일을 찾아 실행

만약 uproject가 연결되지 않았다면  
에픽 게임즈 런처를 통해 다시 등록할 수 있다.

---

## 에디터 버전 정보 관리 구조

### uproject 파일

uproject 파일은 **텍스트(JSON) 파일**이다.

```text
    {
        "FileVersion": 3,
        "EngineAssociation": "5.1"
    }
```

- EngineAssociation 값으로 엔진 버전을 지정
- 이 정보 기준으로 에디터가 선택됨

### 런처의 엔진 정보

에픽게임즈 런처는 시스템에 설치된 언리얼 엔진들의 정보를 별도의 데이터 파일로 관리한다.

- LauncherInstalled.dat 파일에 저장됨
- 설치된 언리얼 엔진의 **버전 정보와 실제 설치 경로**가 기록되어 있음

언리얼 에디터를 실행할 때, UnrealVersionSelector는 이 정보를 참조하여 uproject 파일에 지정된 엔진 버전에 대응되는 에디터를 찾아 실행한다.

즉, 런처는 단순한 다운로드 도구가 아니라 **여러 엔진 버전을 동시에 관리하고, 프로젝트와 엔진을 연결해주는 역할**을 수행한다.

---

## 프로젝트 폴더 자동 생성 구조

uproject 파일을 실행하면 언리얼 에디터가 **표준 프로젝트 폴더 구조**를 자동 생성한다.

### 주요 폴더

Config  
- 프로젝트 설정 파일 보관

Content  
- 모든 에셋(메시, 머티리얼, 블루프린트 등) 보관

DerivedDataCache  
- 에셋의 변환 결과를 캐싱
- 로딩 속도를 빠르게 하기 위한 용도
- 용량이 크면 삭제해도 무방하다 (자동 재생성)

Intermediate  
- 빌드 중 생성되는 중간 결과물
- 언제든지 삭제 가능

Saved  
- 임시 저장 데이터
- 의도적으로 저장한 것이 아니라면 삭제해도 문제 없음

## 블루프린트 프로젝트

블루프린트 프로젝트란 **개발자가 직접 작성한 C++ 코드가 하나도 없는 언리얼 프로젝트**를 의미한다.
여기서 중요한 점은 **C++을 전혀 사용하지 않는다**는 뜻이 아니라, **개발자가 C++ 코드를 추가하지 않았다는 의미**라는 것이다.

언리얼 엔진은 게임 제작에 필요한 대부분의 기능을 이미 **엔진 내부의 C++ 모듈 형태**로 제공하고 있다.
블루프린트 프로젝트는 이러한 구조를 기반으로 구성된다.

- 언리얼 엔진이 제공하는 C++ 모듈을 그대로 사용하고
- 해당 모듈의 클래스들을 상속받아
- 블루프린트로 기능과 게임 로직을 구성하는 방식이다

블루프린트 프로젝트의 특징

- C++ 빌드 환경 없이도 바로 개발 가능
- 컴파일 없이 로직을 수정하고 즉시 테스트 가능
- 빠른 프로토타이핑과 기획 검증에 매우 유리

블루프린트 프로젝트라고 해서 구조가 고정되는 것은 아니다.

프로젝트 진행 중 필요해지면 **언제든지 개발자 C++ 모듈을 추가하여 C++ 프로젝트로 확장할 수 있으며**, 이 경우에도 기존 블루프린트 로직은 그대로 유지된다.

---

## 언리얼 C++ 모듈

### 모듈 기반 구조

언리얼 엔진의 모든 소스 코드는 **모듈 단위**로 구성되어 있다.

- 모듈은 하나의 기능 단위를 캡슐화한 구성 요소이며
- 게임과 에디터에서 실행되는 모든 로직은 이 모듈들을 컴파일한 결과물이다

### 모듈의 결과물

언리얼 모듈은 어떤 타겟으로 빌드되느냐에 따라 서로 다른 형태의 결과물을 생성한다.

- 에디터 타겟으로 빌드된 모듈은 에디터 실행 중에 로드되는 **DLL(동적 라이브러리)** 형태로 생성된다
- 게임 타겟으로 빌드된 모듈은 실행 파일에 포함되는 **정적 라이브러리** 형태로 빌드된다

에디터용 모듈은 `UnrealEditor-모듈이름.dll`과 같은 이름 규칙을 따른다.

---

## C++ 모듈 추가 방식

직접 제작한 C++ 모듈을 에디터에 추가하려면 다음 조건을 만족해야 한다.

- DLL을 Binaries/Win64 폴더에 배치
- UnrealEditor.modules 파일도 함께 배치
- uproject 파일에 모듈 정보 명시

```text
    {
        "FileVersion": 3,
        "EngineAssociation": "5.1",
        "Modules": [
            {
                "Name": "모듈이름",
                "Type": "Runtime"
            }
        ]
    }
```

## Source 폴더와 빌드 시스템

언리얼 프로젝트에서 소스 코드는 단순히 Visual Studio 솔루션에 종속된 형태로 관리되지 않는다.

언리얼의 실제 빌드는 Visual Studio가 아니라 **Unreal Build Tool(UBT)** 이라는 별도의 빌드 시스템이 담당한다.

UBT는 C#으로 작성된 프로그램이며, 특정 IDE에 의존하지 않고 멀티 플랫폼 빌드를 지원하기 위해 설계되었다. Visual Studio 프로젝트 파일 역시 UBT가 생성해주는 결과물 중 하나에 불과하다.

---

## Source 폴더의 역할과 구성

Source 폴더는 **언리얼 빌드 시스템이 참조하는 유일한 C++ 소스 관리 기준 위치**이다.

이 폴더 안에는 다음 정보들이 함께 존재한다.

- 어떤 실행 파일을 만들 것인지에 대한 **타겟 설정**
- 프로젝트를 구성하는 **모듈 정의**
- 각 모듈의 빌드 규칙과 C++ 소스 코드

즉, Source 폴더의 구조만 올바르게 유지된다면 IDE 설정이나 중간 산출물은 언제든지 다시 생성할 수 있다.

---

## 타겟 설정 파일과 모듈 설정 파일

언리얼은 빌드 대상을 **타겟(Target)** 단위로 구분한다.

타겟 설정 파일은 **이 프로젝트에서 어떤 실행 파일을 만들 것인가**를 정의한다.

- {프로젝트명}.Target.cs  
    실제 게임 실행 파일을 만들기 위한 설정

- {프로젝트명}Editor.Target.cs  
  언리얼 에디터 실행 파일을 만들기 위한 설정

이 타겟 설정을 기반으로, 각 타겟에 포함될 **모듈들이 어떤 방식으로 빌드될지**를 모듈 설정 파일(.Build.cs)에서 정의한다.

.Build.cs 파일에서는

- 어떤 모듈에 의존하는지
- 어떤 헤더를 공개할지
- 어떤 빌드 옵션을 사용할지

와 같은 **모듈 단위의 빌드 규칙**을 지정한다.

---

## 모듈 구현과 주 게임 모듈

각 모듈은 C++ 코드로 구현되며, 모듈의 성격에 따라 서로 다른 초기화 매크로를 사용한다.

이 중 가장 중요한 것은 **주 게임 모듈(Primary Game Module)** 이다.

- 프로젝트의 중심이 되는 모듈
- 게임 실행 시 가장 먼저 로드되는 모듈
- 일반적으로 프로젝트당 하나만 존재

이 모듈을 기준으로 다른 기능 모듈들이 종속 관계를 형성하며 프로젝트가 구성된다.

---

## 프로젝트 파일 생성과 Intermediate 폴더

uproject 파일에서 Generate Visual Studio project files 를 실행하면

- UnrealVersionSelector가 동작하고
- Unreal Build Tool이 Source 구조를 분석하여
- Intermediate 폴더에 IDE용 프로젝트 파일을 생성한다

Intermediate 폴더는 언제든지 삭제 후 재생성할 수 있는 **중간 산출물**이며, 실제 프로젝트의 기준은 항상 Source 폴더이다.

---

## 모듈 간 종속 관계와 접근 제어

언리얼 프로젝트는 여러 모듈이 서로 의존하는 구조로 확장된다.
이때, 불필요한 의존성을 줄이기 위해 모듈 내부 소스는 명확히 구분해서 관리한다.

- Public  
    외부 모듈에서 접근 가능한 인터페이스

- Private  
    모듈 내부 구현 전용 코드

외부로 공개되는 클래스에는 {모듈이름}_DLL 매크로를 사용하여 링크 범위와 심볼 공개를 명확히 지정해야 한다.

프로젝트가 커질수록 기능 단위로 모듈을 분리하고, 공개 범위를 최소화하는 구조가 중요해진다.

## 플러그인 시스템

언리얼 프로젝트에 기능을 추가하는 방법은 단순히 Source 폴더에 모듈을 늘리는 것만으로는 한계가 있다.

프로젝트 내부 모듈 방식은 다음과 같은 구조적 한계를 가진다.

- 프로젝트에 강하게 결합되어 있다
- 다른 프로젝트로 옮기기 어렵다
- 팀 단위 분업이나 기능 재사용에 불리하다

이러한 문제를 해결하기 위해 언리얼 엔진은 **플러그인(Plugin) 시스템**을 제공한다.

플러그인은 모듈과 콘텐츠를 하나의 단위로 묶어 프로젝트와 독립적으로 관리할 수 있도록 만든 구조이다.

### 플러그인의 구조와 역할

플러그인은 단순한 코드 묶음이 아니라, 다음 요소들을 함께 포함할 수 있는 **패키징 단위**이다.

- 플러그인 명세를 정의하는 uplugin 파일
- 하나 이상의 C++ 모듈
- 플러그인 전용 콘텐츠
- 에디터에서 사용되는 리소스 (아이콘, 메뉴 등)

이 구조를 통해 플러그인은 다음과 같은 개발 방식을 유연하게 지원한다.

- 프로젝트 간 기능 재사용
- 팀 단위 분업 개발
- 필요에 따른 기능의 활성 / 비활성

플러그인은 프로젝트의 Plugins 폴더 아래에 배치되며, 에디터 설정을 통해 쉽게 추가하거나 제거할 수 있다.

### uplugin 파일의 역할

uplugin 파일은 플러그인의 성격과 구성 정보를 정의하는 **명세 파일**이다.

이 파일을 통해 언리얼 에디터와 빌드 시스템은 다음 정보를 파악한다.

- 플러그인의 이름과 버전
- 포함된 모듈 목록
- 각 모듈의 로딩 시점과 타입

즉, uplugin 파일은 플러그인이 어떻게 로드되고, 어떤 시점에 어떤 모듈이 활성화되는지를 결정하는 기준이 된다.

### uplugin 파일 예시

```text
{
    "FileVersion": 3,
    "Version": 1,
    "VersionName": "1.0",
    "FriendlyName": "GameUtility",
    "Modules": [
        {
            "Name": "CommonUtility",
            "Type": "Runtime",
            "LoadingPhase": "Default"
        }
    ]
}
```

위 예시는 GameUtility라는 플러그인이 CommonUtility라는 Runtime 모듈 하나를 포함하고 있으며, 엔진 초기화 과정의 기본 단계에서 로드됨을 의미한다.

## 플러그인과 프로젝트 모듈의 차이

프로젝트 모듈과 플러그인은 기능을 추가하는 방식이라는 점에서는 같지만, 프로젝트와의 결합도와 사용 목적에서 차이가 있다.

- 프로젝트 모듈  
    - 프로젝트 내부에 종속된 기능 구현 방식  
    - 해당 프로젝트를 기준으로 설계되고 관리된다

- 플러그인  
    - 프로젝트와 분리된 독립적인 기능 단위  
    - 여러 프로젝트에서 재사용 가능하며 분업에 적합하다

프로젝트 규모가 커질수록, 또는 공통 기능을 여러 프로젝트에서 함께 사용해야 할수록 플러그인 구조의 중요성은 더욱 커진다.

## 게임 빌드

게임을 사용자에게 배포하기 위해서는 에디터 환경이 아닌 **독립적으로 실행 가능한 게임 프로그램**을 만들어야 한다.

이를 위해 언리얼에서는 게임 타겟 설정을 기준으로 한 빌드 파이프라인을 제공하며, 이 과정은 다음 세 단계로 구분해 이해할 수 있다.

- 빌드(Build): 게임 실행 파일을 생성하기 위한 컴파일 단계
- 쿠킹(Cooking): 배포할 플랫폼에 맞게 콘텐츠 에셋을 변환하는 단계
- 패키징(Packaging): 실행 파일과 쿠킹된 에셋을 묶어 하나의 게임 프로그램으로 만드는 단계

### 게임 타겟 빌드

게임 타겟으로 빌드를 수행하면 프로젝트의 모듈들은 에디터용 DLL이 아니라 **정적 라이브러리 형태로 컴파일되어 실행 파일에 포함**된다.

이 단계에서 생성되는 결과물은 게임 로직이 포함된 **실행 파일(EXE)** 이다.
다만, 이 실행 파일은 아직 콘텐츠 에셋이 포함되지 않은 상태이기 때문에 단독으로는 정상적인 게임 실행이 어렵다.

### 쿠킹과 패키징

실행 파일 생성 이후에는 게임에 사용되는 콘텐츠 에셋을 배포할 플랫폼에 맞게 변환해야 한다.

이 과정을 **쿠킹(Cooking)** 이라고 하며, 텍스처, 메시, 사운드, 맵 등의 에셋이 플랫폼별 실행 가능한 형태로 변환된다.

이후, 실행 파일과 쿠킹된 콘텐츠 에셋을 하나로 묶어 사용자가 바로 실행할 수 있는 형태로 만드는 과정을 **패키징(Packaging)** 이라고 한다.

### Shipping 빌드

Shipping 빌드는 사용자에게 배포할 **최종 게임 코드**를 생성하는 빌드 설정이다.  
이 설정에서는 모든 코드가 최적화되어 빌드되고,check(), ensure()와 같은 어설션 매크로는 제거된다.

### 최종 게임 패키지 생성

실행 파일만 생성된 상태에서는 아직 쿠킹과 패키징이 완료되지 않았기 때문에 최종 배포용 게임이 완성된 것이 아니다.

언리얼 에디터에서 Platforms -> Windows -> Package Project를 실행하면 게임 빌드, 콘텐츠 쿠킹, 패키징 과정이 순차적으로 진행되고, 지정한 폴더에 **최종 게임 패키지**가 생성된다.

이 결과물은 에디터와 완전히 분리된 독립 실행 게임 프로그램이다.
